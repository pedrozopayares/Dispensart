# Tasks — add-dispensation (S3)

Tier A. `[MUT]` declarados: 14 (M1–M14). Refinado por el architect con `design.md` (D1–D10).
"Cimiento" marca andamiaje o registro sin escenario propio: se verifica con el comando que la tarea nombra.
Orden: 0 → 1 → 2 → 3 → 4 → 5 → 6 (solo `software/api`; sin web ni devops: las pantallas son de S6). Un solo
implementador (backend): sin bloques paralelos api ∥ web. Dentro de api, 4.2–4.4 (logs) no dependen de 2–3 y
pueden adelantarse; 5.x depende de 3.x y 4.1. Sección 3 reordenada: el almacén de idempotencia (antes 3.8) pasa a
3.5 porque la acción de dispensar lo consume.
Pruebas del backend: Pest contra PostgreSQL, nunca SQLite. Autorización por rol con `actingAs` (D2 de S1); los
casos CSRF con `tests/Support/SpaClient`. Las pruebas de carrera usan conexiones reales en paralelo con filas
confirmadas, fuera de la transacción de `RefreshDatabase`; kardex y bitácoras rechazan `DELETE`/`TRUNCATE`, así
que el architect fija cómo se limpian esas pruebas (mismo problema que S2).
