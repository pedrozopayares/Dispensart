# Tasks — add-transfers (S4)

Tier A. `[MUT]` declarados: 17 (M1–M17). Borrador del spec-engineer; el architect lo refina con `design.md`.
Requisito previo: S1, S2 y S3 archivados (capacidades `transfers.*`, render de rechazos, `BusinessCalendar`,
`SpaClient`; existencias, kardex, costura única de escritura de stock con su orden global de bloqueo, render de
`insufficient_stock` y `lot_expired`, prueba de carrera con procesos reales; bitácora de operaciones sensibles y
dispensación). Todo es `software/api`: un solo bloque, sin trabajo de `web` (pantalla en S6).
Pruebas: Pest contra PostgreSQL, nunca SQLite. Roles con `actingAs`; CSRF con `SpaClient`. `RefreshDatabase` por
defecto; carreras con `DatabaseMigrations` y filas dedicadas por iteración (como S2). Toda escritura de stock pasa
por la costura de S2; ningún `FOR UPDATE` propio sobre existencias. Orden de bloqueo (design D4): una sola cabecera
(traslado, o solo la discrepancia al resolver) → existencias por la clave global de S2, nunca al revés.
Escenarios citados como «Requisito: escenario» de `specs/transfers/spec.md`; decisiones como D<n> de `design.md`.
Orden de bloques: 0 → (1 ∥ 2) → (3 ∥ 4) → 5 → 6. Paralelismo solo dentro de `api` (un implementador puede
intercalar 3 y 4); no hay bloque `web`, así que no aplica la regla api ∥ web.
